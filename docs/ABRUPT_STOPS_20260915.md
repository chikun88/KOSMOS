# 一時停止の実測調査と、デモの処理待ち修正

**実機の急停止そのものは未解決。** 詳細ログから衝突監視による短いゼロ指令を
特定したが、その近距離検知が実障害物か自己反射かを記録だけで確定できなかった。
検知を無視する修正、自己反射マスクの拡大、非常停止・鮮度閾値の緩和はしていない。
デモで計算待ちが計測輪更新を止める独立した不具合を修正した。

## 実機ログ

2026-09-14 の完了済み実機走行4本（085822、090917、092129、093644）を解析。
最新の140035はhardware起動だが走行していないため、移動の根拠には使わなかった。
150230はdemoであり、実機とは分けた。

指令はDDS発行時刻、計測輪は計測時刻、ROSログはログ内時刻を使う。
受信コールバック時刻を指令発行時刻の代わりにしていない。
各生ファイルの読取範囲とSHA-256、記録終了状態、時計差の検査結果を
[解析JSON](abrupt_stop_evidence_20260915.json)に保存した。
ROS受信時計とUNIX受信時計の差が20msを超える行が各実機ログに2〜10件あるため、
異種時計のミリ秒単位の前後関係や応答遅延を確定する用途には使わない。

「直前の並進指令が0.1m/s超、250ms以内の次サンプルで全成分ゼロ、
500ms以内に非ゼロへ戻る」箇所を抽出した。これは記録上のパルスであり、
目標数・故障率・独立した停止回数を意味しない。

| 実機セッション先頭 | 衝突監視後のパルス | 最終指令のパルス |
|---|---:|---:|
| 085822 | 5 | 5 |
| 090917 | 1 | 1 |
| 092129 | 1 | 1 |
| 093644 | 1 | 0 |

同じ条件で上流の追従指令・RL出力にはパルスがない。
最終段で捕捉されなかった1件を、モーターも停止した証拠として数えていない。
アイドル中に繰り返されるSTALE_COMMANDの件数も移動中の停止率には換算しない。

例：092129の開始35.242秒後、最終指令の並進速度が約0.683m/sからゼロへ落ち、
11ms後に非ゼロへ復帰した。35.225秒には衝突監視がAPPROACHを報告している。
計測輪にもその後の減速が見えるが、速度の外れ値や通信・駆動遅延があるため
実機加速度の確定値は出していない。

この直前、後方LiDARの計測時刻34.990秒の1スキャンに、ビーム961〜985で
約0.337〜0.419mの近距離反射が現れる。同方向の前後のスキャンは無反射。
強度フィールドは47。ただし、同梱SDKのcapsule展開には非ゼロ距離から47を生成する
処理があるため、この値を独立した反射品質の証拠にはできない。
単に品質ゼロの無効データとして取り除けるサンプルでもない。
[生スキャン抜粋](abrupt_stop_scan_excerpt_20260915.json)に前後の同じビームを残した。
一過性という理由だけで障害物を消すことはしていない。

Nav2のAPPROACHが予測衝突時刻に応じて指令全体を縮小することは
[Nav2 1.3.12の実装](https://github.com/ros-navigation/navigation2/blob/1.3.12/nav2_collision_monitor/src/collision_monitor_node.cpp)
でも確認した。ただし、今回の記録には監視入力のフィルタ済みスキャンと
使用フットプリントがないため、監視内部の判定を完全には再現できない。

## 修正と追加記録

- `synthetic_scan_node.py`：スキャン計算を別のコールバックグループへ移し、
  2スレッドのexecutorで実行。指令受信と計測輪更新は同じグループで直列処理し、
  スキャンの計算待ちから分離する。前後LiDARには同一の姿勢スナップショットを使う。
  実機のmeasurement_wheelノードは変更していない。
- `run_recorder_node.py`：衝突監視状態、実際のフィルタ済み前後スキャン、
  local_costmapが公開するフットプリントと時刻を追加記録する。
  生スキャンも保持する。追加スキャンのトピックは`collision_scan_topics`で指定できる。
  記録容量上限は既存値のままなので、保存可能な時間は短くなり得る。
- `scripts/inspect_abrupt_stops.py`：ROS不要の再解析ツール。未完了の記録は
  読取開始時のファイル長で区切り、欠けた末尾行と発行時計の欠損を明示する。

150230のデモ記録にはODOMETRY_STALE状態メッセージ158件があった。
これは158回の独立した停止を意味せず、すべてが上記の競合によると確定したわけでもない。
同条件の全経路走行による修正前後比較は未実施。

## 検証

関連テスト39件成功。スキャン計算を350ms止める実ROS executor試験で、
従来のコールバック共有ではその間の移動指令受信・計測輪更新が止まることを再現。
分離後は同じ負荷中も移動指令を受信し、計測輪更新が継続することを確認した。
追加の衝突監視データ3種類は実DDS送受信で保存内容と時刻を確認した。
既存のRuntimeGuardとLiDAR鮮度の関連試験も成功。
ログ：`logs/abrupt-stops/tests.log`。
`colcon build --symlink-install --packages-up-to omni_autonomy_next`も3パッケージ成功。
ビルドログ：`logs/abrupt-stops/build.log`。

この変更は次回起動から有効。実行中のロボットへの再起動・走行指令は送っていない。
実機側は停止時の人・荷物・配線や可動機構の状況との照合が必要。
現在の記録だけを根拠に「実機のカクンが直った」とは言えない。

## 操作者情報を踏まえた追加調査

操作者から「すべて同じ一過性検知による停止なら、実際には障害物はなかったと思う」
との情報を得た。この条件付きの情報と整合する自己反射を第一候補として、
前回抽出した8箇所の前後両LiDARを比較した。

| セッション | 衝突監視後ゼロ時刻（開始から秒） | 機体際の一過性反射が見つかった側 | レーザー座標の角度・距離の例 |
|---|---:|---|---|
| 085822 | 49.028 | 後方 | 136〜138度、0.634〜0.678m |
| 085822 | 116.599 | 後方 | 148度付近、0.304m |
| 085822 | 132.927 | 後方 | 137〜139度、0.518〜0.554m |
| 085822 | 217.380 | 前方 | 145〜156度、0.289〜0.333m |
| 085822 | 251.073 | 前方 | 154〜159度、0.285〜0.345m |
| 090917 | 36.556 | 後方 | 約138度、0.497m（2ビーム） |
| 092129 | 35.225 | 後方 | 142〜149度、0.337〜0.419m |
| 093644 | 103.724 | 前方 | 144〜149度、0.310〜0.328m |

後方5箇所・前方3箇所であり、「全部が後方」ではなかった。
前後センサーの取り付けはほぼ180度対称で、これらは機体座標では左右の縁付近に集まる。
093644ではその前のスキャンにも約0.18mの反射があり、「必ず1スキャンだけ」とも言えない。
090917は周囲の継続した近接点もあるため、全点を異常反射として扱ってはいけない。
以前の「隣接3ビーム以上・前後とも急に遠くなる」という探索では、この2ビームと
連続2スキャンのケースを十分に拾えていなかった。

この対応は自己反射の疑いを強めるが、監視が使用したフィルタ済み点・TFがないため、
各ゼロ出力の直接の原因点を確定するものではない。
この8箇所以外の停止や、時計・通信・自己位置異常による停止まで説明する結果ではない。
今回の追調査では制御・検知パラメーターは変更していない。

再現ツール：`scripts/inspect_stop_scan_windows.py`。
原データのSHA-256を検証し、既存の50mmレーザー方向の自己反射除去を適用したうえで、
機体中心0.85m以内・停止周辺の点を**診断用の候補**として列挙する。
この0.85mや上表の角度・距離は、障害物を除去するための設定値ではない。
結果：[各停止の前後スキャン](stop_scan_windows_20260915.json)。

```bash
python3 scripts/inspect_abrupt_stops.py \

```
