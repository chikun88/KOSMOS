# 2026-09-05 制御の連続性・再発進の修正

SSHでegg8PCとbacon6の既存リポジトリを修正した。既存の未コミット変更は維持。
ソフトウェア検証とモーター出力なしの統合試験を完了した。
実機の高速走行・駆動系較正・全地点の走行保証は、この検証には含まれない。

## 場所に依存しない減速・復帰不良

ユーザーから「場所に関係なく途中で遅くなる」と確認した。
9月4日の実センサー・モーター有効構成のログには、16:58開始の回で
`STALE_COMMAND`が72回、17:21開始の回で51回記録されている。
これは状態遷移の記録数であり、待機中も含むため、走行中のパケット欠落数とは違う。
これらのログだけでは、最初の指令遅延がどの段で発生したかは断定できない。

一方、指令途切れ後に復帰できなくなる循環はコードと再現試験で確認できた。

1. RuntimeGuardが古い指令を拒否し、`applied_scale=0`を報告する。
2. 追従器がこの値で参照時計まで停止する。
3. 停止位置から再計画すると、初速・位置誤差ともゼロになり、新しい非ゼロ指令を生成できない。
4. Collision Monitorも、繰り返すゼロ指令の配信を一定時間後に止めるため、RuntimeGuardは新しい指令を待ち続ける。

配備版Nav2 1.3.12の動作は
[publishVelocityの公式実装](https://github.com/ros-navigation/navigation2/blob/1.3.12/nav2_collision_monitor/src/collision_monitor_node.cpp#L197-L217)
で確認した。設定の`stop_pub_timeout`は0.50秒。

修正後は、実際に出力する倍率`applied_scale`と、参照計算用の`reference_scale`を分ける。
ARM・非常停止・自己位置・RL・モーターリンク・自動制御許可のすべてが正常なら、
参照計算は設定倍率で新しい指令を作れる。指令の古さによる出力停止、衝突監視、
加速度・車輪速度制限は引き続きRuntimeGuardとCollision Monitorが適用する。
参照の先行距離上限も維持する。ユーザー倍率ゼロや各インターロック異常時には参照時計も停止する。

停止・同位置再計画という条件を固定した比較では、修正前の新しい前進参照は
0 m/s、修正後は0.020825 m/sとなり、衝突監視で再評価できる。
RuntimeGuardは新しい検査済み指令が届くまで出力ゼロを維持する。

以後の切り分け用に、状態へ`command_age_sec`・`health_reason`・`reference_scale`を追加。
停止への状態遷移ログにも指令年齢・健康状態・ユーザー倍率を記録する。
最初の遅延自体が完全に解消したとは主張しない。

## 短距離・回転・終点の修正

- 再サンプリングは非ゼロ距離に最低3点を置く。2点だけでは両端の速度がゼロになり、
  4 cmに400秒の速度計画を作っていた。修正後の同じ数値条件では0.433861秒。
  これは参照軌道の所要時間であり、実機到着時間ではない。
- 加減速区間は等加速度の式で位置と速度を同時に計算する。
  再計画時の時刻合わせ・参照先行制限にも同じ式の逆関数を使う。
- 経路上の進捗を、最寄りの5 cm刻みの頂点から線分上への連続投影に変更した。
- 終端の向きは、遅れた参照時計から独立して最終目標へ寄せる。
  20 cmから10 cmの区間で滑らかに切り替え、終端サーボへの切替で角速度を急変させない。
  回転・並進の出力加速度制限も継続する。

旋回方法は、動的計画法による姿勢最適化と単純な向きの補間を再比較した。
120 msの無駄時間・80 msの一次遅れ・20 Hz制御の単体モデルでは、単純補間が
90度回転を伴う2区間で5.78秒/4.44秒、最適化が5.95秒/4.73秒だった。
同じ向きでの移動では双方5.84秒。複雑化による速度向上は確認できず、
`optimize_yaw=false`を維持する。これらは障害物回避を含む実フィールド走行時間ではない。
既存の固定進入・退出レーンも維持する。
