# 高速モード：4 m/s要求・各輪上限9000

ユーザー指定に基づき、`sprint` の速度要求を前後・左右4.0 m/s、
UART各輪指令上限を9000に変更した。通常の `balanced` と `precision` は
2.0 m/s・8000を維持する。既定モードは `balanced`。
次回起動後、GUIのプロファイルを `sprint` にすると適用される。
実機走行試験・再起動は行っていない。

## 実装

- RuntimeGuardのhard上限とNav2の基準速度を4.0 m/sへ同期。
  プロファイル別の速度制限で通常モードを2.0 m/sに制限する。
- trackerとRuntimeGuardの公称車輪予算を高速モードだけ切り替える。
  通常へ戻すと既存の車輪予算へ戻る。
- モーター送信ノードが `/system/profile` を購読し、`sprint` のときだけ
  UARTミキサへ9000を指定する。未受信・未知のモード・通常モードは8000。
  前後・左右・旋回を合成した後、全輪を比例縮小して指定上限内へ収める。
  既定のv4 UARTパススルー経路が対象。旧v3経路の既定上限は8000。
- C++側ミキサにも同じ任意上限を実装。v4ではJetsonが作ったフレームを
  そのまま転送するため、Piの再配置は今回のv4上限変更に必要ない。
- Nav2の1.2秒予測が地図内に収まるよう局所地図を8 m四方から12 m四方へ変更。
  地図セル数は2.25倍となり、実機の処理負荷は未測定。
- 送信補正0.38/0.34、加減速、残り距離による制動、曲率、局所速度制限、
  障害物監視は従来どおり適用する。バケツ入口等の2 m/s制限も残る。

## 9000で4 m/sに届くか

純軸方向4 m/s要求で必要な指令は `4 × 0.38 × 7202 = 10947.04`。
9000上限により約0.822倍へ縮小される。斜め移動や同時旋回はさらに出力を使う。
補正や計測輪換算を変えて速度表示だけを増やす変更は行っていない。

[8条件の候補比較](four_mps_replay_20260915.json)は、最新2本の実機応答ゲイン、
前後・左右、上限8000/9000を組み合わせ、60 mの仮想直線で4 m/s要求を評価した。

| 各輪上限 | モデル速度のピーク範囲 |
|---|---:|
| 8000 | 2.891〜3.027 m/s |
| 9000 | 3.251〜3.404 m/s |

全8条件が仮想終点へ到達した。9000条件の送信ピークは全て9000。
**モデルでも4 m/s未達、実機4 m/sは未達成・未検証。**
これは低速の実機記録からの線形外挿で、高速時の滑り・電源降下・負荷変化を含まない。
記録欠落を含み、Nav2・実フィールド障害物・LiDAR衝突監視を通した走行結果ではない。
リプレイでは候補上限をメモリ内で上書きし、実制御tickとUART飽和を機体応答へ適用する。
モード切替と実際のv4エンコードは別の回帰テストで検証する。

現行制動モデル（減速度0.6375 m/s²、遅れ0.38秒）では、4 m/sから停止まで
約14.07 m、静止から加速して停止するには約23.48 m必要。
局所地図拡張は検知距離や実測停止距離の保証ではない。
短い実フィールド経路では残り距離・局所制限によって要求速度以下になる。
9000の指定範囲内で速度を引き上げる設定であり、4 m/s達成の保証ではない。

## 再現

```bash
source /opt/ros/jazzy/setup.bash
source ros2_ws/install/setup.bash
OPENBLAS_NUM_THREADS=1 python3 scripts/check_speed_target_replay.py \
  --audit docs/six_mps_audit_20260915.json --targets 4 --uart-limits 8000 9000 \
  --output docs/four_mps_replay_20260915.json
python3 -m pytest -q ros2_ws/src/omni_autonomy_next/test/test_sprint_speed.py
cmake --build bacon_gateway/build -j 2
ctest --test-dir bacon_gateway/build --output-on-failure
```

  今回は停止確認の既存実装・テストの期待時刻を変更していない。
