# 実機走行データの自動回収

通常の `起動.sh` / `python3 run.py full` / `real` / `demo` 起動で、
独立した `run_recorder` プロセスが自動起動します。走行前の待機から停止・終了まで、
受信したメッセージを間引かず保存します。実機の走行操作は従来どおりです。

保存先は `~/.ros/omni_autonomy_next/runs/<UTC日時>-<ID>/` です。
起動ログにも `Run recording: ...` と表示します。各フォルダーを丸ごと回収してください。
直接 `ros2 launch` を使う場合は `run_log_directory:=/保存先` で変更でき、
`record_runs:=false` で記録を無効にできます。

## 記録内容

- 制御各段の速度指令：Nav2、軌道追従、RL補正、衝突回避後、最終安全指令。
- 計測輪：カウンター生値・差分、位置・速度・共分散、読み取り状態。
- 自己位置：位置・姿勢・共分散、追跡正常信号、診断情報、TF。
- 経路・目標：経路全点、目標姿勢、目標番号要求、成功・失敗・キャンセル、
  記憶地点、フィールド選択、走行モード、軌道追従状態。
- 安全制御：アーム、非常停止、停止理由、速度倍率、プロファイル、速度上限。
- 衝突監視（2026-09-15追加）：`/collision_monitor/state`の判定とポリゴン名、
  `/scan_front_filtered`・`/scan_rear_filtered`の実入力、
  `/local_costmap/published_footprint`の輪郭・座標系・時刻。
  フィルタ済みスキャンの対象は`collision_scan_topics`で変更できる。
- モーター：ブリッジが公開するテレメトリ、通信状態・遅延、自動制御接続状態。
- 前後LiDAR：全距離配列・強度・角度・スキャン時間・フレーム。
- 設定：起動時の設定ファイル本文とSHA-256、ソースファイルのSHA-256、
  取得可能ならGit版と変更状態、起動モード、実行中パラメーター、変更イベント、ROSログ。

`manifest.json` に記録対象の実際のトピック名・型・QoS、設定の写しを保存します。
実行中のパラメーターは10秒周期でノードを探索して非同期取得し、ノードごとに約60秒周期で
再取得します。サービスが応答しないノードの値は取得できません。変更イベントも別途記録します。
モーターの実回転数・電流など、現在の機器がROSに公開しない情報を推定値で補うことはしません。

## ファイルと時刻

- `samples-0000.jsonl` 以降：1行1メッセージのJSON（schema 2）。
  `topic`、`type`、`sequence`、受信単調時刻 `monotonic_ns`、受信ROS時刻
  `received_ros_ns`、受信UNIX時刻 `received_unix_ns`、メッセージ全体 `value` を記録します。
  headerのあるメッセージは発行時刻 `source_ros_ns` も記録します。
  2026-09-14の実走行解析後は、headerのない指令にもDDSの発行時刻
  `published_unix_ns` とDDS受信時刻 `dds_received_unix_ns` を追加しています。
  内部のパラメーター取得記録は `recorder/parameter_snapshot` です。
- `recording-summary.json`：書き込み件数・トピック別件数・欠落件数・未処理件数・
  書き込みエラー・終了状態。記録中も約1秒ごとに更新します。
- `manifest.json`：起動時情報。`operation_mode` で `hardware`、
  `hardware_motor_off`、`demo` を区別します。単独起動は `unknown` です。
  これは起動指定の区別であり、実際に動いた証拠はテレメトリ・計測輪で確認してください。

速度はm/sとrad/s、距離はmです。座標系・共分散は元メッセージを保持します。
JSONで非有限値を壊さないよう、LiDARの無反射・無効値などは文字列
`"Infinity"`、`"-Infinity"`、`"NaN"` として区別します。

## CSVへの変換

走行終了後、ROSのないPCでも実行できます。

```bash
python3 scripts/analyze_run.py ~/.ros/omni_autonomy_next/runs/<回収フォルダー>
```

同じフォルダーに `control.csv` と `analysis.json` を生成します。
CSVは計測輪の各速度サンプルに対し、各制御段で直前に受信した指令とその経過時間、
最終指令に対する速度偏差を並べます。0.25秒より古い指令は欠損として扱い、
未来の指令を対応付けません。閾値は `--max-command-age 0.25` で変更できます。
サマリーには指令との速度RMSE、対応付けできなかった件数、トピックごとの最大受信間隔を出します。

この対応付けは受信時刻基準で、機体の応答遅れを補正していません。
実走行では記録側のコールバック待ちが最大数秒ありました。発行・計測時刻から
受信まで250 msを超える場合、`analysis.json` に `receipt_alignment_warning` を出します。
このCSVの速度比をそのまま較正に使わないでください。今回のv4実機データを
発行・計測時刻で対応付ける手順は [実走行応答の改善](FIELD_RESPONSE_20260914.md) にあります。
RMSEだけで制御改善を判定せず、同じ経路・速度倍率・荷重・モードで比較してください。
発行時刻、状態遷移、経路、自己位置、スキャンを使った詳細解析にはJSONLを使います。
原データは変換後も残ります。途中で強制終了して末尾1行が欠けた場合、解析はその行を数えてスキップします。

## 容量と記録品質

既定は1ファイル64 MiB、1起動あたり最大32ファイル（2 GiB）、空き容量512 MiBを確保します。
上限到達時は記録を停止し、既存データを削除しません。複数起動分も自動削除しません。
設定パラメーターは `segment_mb`、`max_segments`、`reserve_mb`、`queue_size` です。
大量のスキャンを含むため、長時間の試験は空き容量とサマリーを確認してください。

速度指令・センサー受信はbest-effortです。保持された目標・状態を途中参加でも受信するため、
transient-localの状態トピックにはreliableを使います。保存用キューは既定4096件です。
キュー満杯では欠落を数え、保存不能・容量不足はROSログにエラー表示します。
`dropped=0` はROS通信経路での欠落がないことを保証しません。トピック別件数と受信間隔も確認します。
電源断では最後の約1秒や未処理キューが失われる可能性があります。
`closed=false`、サマリーなし、`error`、`pending`、`dropped` は不完全な記録として扱ってください。

既存の `python3 run.py record-run` も同じ詳細記録を使い、Ctrl+C時に従来の簡易集計を表示します。
通常起動では自動記録済みなので、追加で実行すると別セッションへの二重記録になります。
