# 広い場所で旋回し、その後は向きを保持する走行方式

既存の `simultaneous` に加えて `staged_heading` を選択できます。既定の方式は
`simultaneous` のままです。GUI の「走行方式（次の目標から）」で選び、目的地を
送信します。運転中の方式変更は次の目標に適用し、実行中の旋回基準を跳ばしません。
現在の方式・段階・停止理由は GUI と `/trajectory_tracker/status` に表示します。

```bash
python3 run.py demo --motion-mode staged_heading --goal-id 4
# センサーを用いる実機構成。従来同様、この real コマンドではモーターを有効化しない。
python3 run.py real --motion-mode staged_heading
# ROS launch を直接使用するとき
ros2 launch omni_autonomy_next system.launch.py motion_mode:=staged_heading
```

`--no-tracker` / `tracker:=false` と新方式の組合せは起動エラーにします。
GUIで新方式を選んでもMPPI構成そのものは切り替わりません。追従器の状態が表示
されている構成で使用してください。

## 動作と制約

1. Nav2 の経路に沿い、現在の向きで旋回地点まで、目標の向きでその先を通れるか
   NORMAL の10頂点フットプリントで検査します。経路の検査間隔は最大10 mm。
   点間の掃引と姿勢誤差0.02 radの分を差し引いた後に25 mmの余裕を要求します。
2. 旋回の途中姿勢を最大0.025 rad刻みで検査します。点間の角移動と25 mmの
   位置余裕を差し引き、さらに120 mm以上余裕のある地点を候補にします。
   余裕350 mmまでは広さを優先し、同程度なら早く回れる地点を選びます。
3. 旋回地点は再計画ごとに動かしません。ゲートまでの並進を停止し、計測輪で
   並進0.02 m/s未満・角速度0.025 rad/s未満が0.30秒続くのを確認します。
4. 最新の局所コストマップで、機体外接円+120 mmが障害物・未知セルに重ならない
   ことを確認して旋回します。odom→mapの座標変換を扱い、地図や変換が取れない
   ときは旋回を止めます。地図は全体配信にし、元のタイムスタンプから0.8秒以内
   であることを確認します。
5. 旋回中の並進指令は常にゼロです。目標方位との差0.008 rad未満と停止を
   0.30秒確認してから、経路を作り直して方位を保持したオムニ移動へ移ります。
   走行中の小さな方位ずれには補正を入れ、0.02 radを超えるずれでは停止します。

新方式ではNav2の復帰Spin/BackUpを中継しません。新しい目標・キャンセルは計画
スレッドの世代番号を更新し、古い計画が復帰して走り出すのを防ぎます。
自己位置・計測輪の欠落や停止指示の後は停止確認の継続時間を再計測します。
複数ゲートを通るNav2の再計画が2秒を超える例があったため、新方式の計画更新待ち
上限は4秒です。キャンセルは別の購読で直ちに反映し、自己位置0.3秒・計測輪0.2秒・
局所地図0.8秒の監視やCollision Monitorの停止条件は延長していません。

これはNav2が提案した経路の周辺での有限な探索です。Smacのセル中心や平滑化に
よる角の切り込みは元の経路から最大120 mm以内で補正し、補正後の全経路を再検査
します。存在しない通路や、現在の向き→一度の旋回→目標の向きという制約では
通れない経路を、通れるとは判定しません。安全な解が見つからない場合は停止して
`NO_SAFE_ROTATION_GATE` / `FIXED_HEADING_PATH_BLOCKED` 等を表示します。
大域的な最短時間や、任意の到達可能な姿勢を必ず発見する保証はありません。

## 固定バケツ2・3の進入改善

固定バケツ2は地点4、固定バケツ3は地点5です。従来の進入ゲートでは、Nav2の
曲線がバケツの角まで斜めに接近することがありました。新しい外側ゲートで先に
`x=-0.80 m`へ合わせ、既存の内側ゲートへ直線で進入します。

| 地点 | 方向 | 外側ゲートY | 内側ゲートY |
|---|---|---:|---:|
| 4 | 上側 | 2.15 | 1.75 |
| 4 | 下側 | 0.50 | 0.75 |
| 5 | 上側 | -1.55 | -1.95 |
| 5 | 下側 | -3.20 | -2.75 |

下側進入は目標のYまでx=-0.80を保持し、その後に最後の10 mmを横移動します。
下側進入のCAD最小余裕は、旧来の斜め接近の約42.3/44.6 mmから48.6 mmへ改善
します。退出は同じゲートを逆順に使います。目標座標は変更していません。
再計画の始点は量子化されたセル中心でなく、その時点の自己位置を使います。

新方式の終端減速域は450 mm、終端速度上限は0.18 m/sです。さらに機体の余裕、
加速度と応答遅れから速度を制限します。壁に近い直線レーンは0.18 m/sを上限とし、
横方向の壁までの距離を前進方向の制動距離と取り違えて過剰に減速しないようにします。
広い直線では選択中のプロファイルと車輪速度の上限を使用します。
最後の出力も遅れ+制動中のCAD掃引で検査し、危険なら
停止します。LiDARの動的障害物は引き続きCollision Monitor、その後の最終指令は
RuntimeGuardを通ります。モーターゲートを迂回する出力は追加していません。
新しい指令だけでなく、計測輪で観測した並進・旋回の慣性が停止するまでの範囲も
独立して確認します。壁から離れる指令を出しただけで、壁へ向かう慣性が消えたとは
扱いません。

追従誤差によって通常の計画余裕の内側に入ってしまった場合、CAD上で機体自体に
30 mm以上の余裕が残り、短い接続経路で通常の余裕へ戻れるときだけ回復を許可します。
計測輪の停止を確認し、旋回指令ゼロ・最大0.05 m/sで余裕が増える方向へ動きます。
壁へ近づく指令や余裕30 mm未満の状態では実行しません。これにより、例えばレーン
から15 mmずれた状態を、そのまま通常速度で続行することも、永久に計画不能とする
ことも避けます。

## 検証と方式の比較

egg8PCの最終回帰テストは319件通過。bacon6ではROSなしで実行できるCAD幾何検査を
実施し、4方向の固定バケツ進入の最小余裕はいずれも48.558 mmでした。

`test_staged_heading.py` は途中姿勢での接触、狭い場所からの退出、ゲート固定、
途中の壁、未知・範囲外の地図、停止要求、24通りの遅延・ゲイン・方位・出発条件、
4方向のバケツ進入、実際に記録したSmacの角の切り込みを検証します。

```bash
python3 -m pytest -q ros2_ws/src/omni_autonomy_next/test
python3 scripts/check_staged_heading_geometry.py
python3 scripts/compare_staged_heading.py
python3 scripts/check_staged_heading_demo.py --initial-pose-id 1 --goal-id 4
```

比較結果は `staged_heading_comparison.json`。同じ追従器の実際の制御周期を、
駆動遅れ120–300 ms、一次遅れ80–150 ms、ゲイン1.0/2.8の模擬プラントで
動かす比較です。地図のない自由空間での制御比較であり、実機の測定値ではありません。
ROSデモは独立したROS_DOMAIN_ID=191で、モーター・実LiDAR・計測輪を無効にして
動かします。初期位置からの到達、各段階と停止理由をJSON/ログに保存します。

自由空間、移動距離約2.06 m、駆動遅れ120 ms+一次遅れ80 ms、ゲイン1.0の比較:

| 方位変更 | 同時旋回の停止到達 | 分離旋回の停止到達 |
|---|---:|---:|
| 90° | 5.02秒 | 13.65秒 |
| 180° | 6.17秒 | 14.50秒 |

この条件で新方式は高速化にはなっていません。両方式とも到着後の位置誤差は
模擬プラント上では1 mm未満でした。新方式は旋回場所と狭い進入時の方位を明確に
制約したい場合の選択肢です。既定の同時旋回を置き換える根拠にはしていません。

固定方位での進入は並進と旋回の干渉を減らせます。ただし停止と旋回の時間が加わる
ため、短い移動や小さな方位変更では同時旋回の方が速い場合があります。新方式も
実機で常に最速・最安定とは断定していません。CAD上の約49 mmは大きな余裕では
なく、実際のバケツ位置、積載状態の機体外形、LiDAR位置推定の誤差を反映した比較
が必要です。今回の作業では物理モーターを駆動していません。
