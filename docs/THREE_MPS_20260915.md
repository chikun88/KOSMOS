# 実走行データによる3 m/s到達条件の調査

**実機3 m/sは未達成・未検証。通常設定は2.0 m/sを保持する。**
既存ログで実際に出た速度、送信の上限、加減速の距離を照合した。
今回変更したのは解析・オフライン検証であり、実機設定の引上げや走行指令送信は行っていない。

## 詳細ログで確認できたこと

日付順だけでは実機ログを選べない。`19700101T000527.028726Z-6ae2b78a`には
2.0 m/s設定、モーター・計測輪・LiDAR有効の実走行が記録されている。
`20260914T163753.204016Z-52cab929`はdemoである。
1970年の記録の暦上の実施日時・新旧関係は、このフォルダー名からは確定しない。

対象は上記の2.0 m/s設定走行、その後のID `19700101T002342.850864Z-0eb2b8a4`、
従来の完了走行 `20260914T093644.887096Z-0970b1be` の3セッション。
記録の設定と生JSONLのSHA-256、各段の集計、時計異常の除外数を
[解析結果](three_mps_audit_20260915.json)に保存した。

2.0 m/s設定の移動記録には216,720件が保存され、26,146件の記録欠落がある。
欠落した時間帯の挙動は復元できず、同定は診断用に限る。
ROS/UNIX時計差20 ms超の行は照合から除外し、CRCを検査したv4送信時計と
計測輪の計測時計を使用した。速度指令の集計にはDDS発行時計を使い、
受信時刻を発行時刻の代用にしない。

| 2.0 m/s設定の移動記録 | 記録中の最大値 |
|---|---:|
| 追従指令 `/cmd_vel_nav_smoothed` | 1.504 m/s |
| 衝突監視後 `/cmd_vel_collision_safe` | 1.155 m/s |
| 最終指令 `/cmd_vel_safe` | 1.095 m/s |
| 補正後の送信速度 | 0.416 m/s |
| UART車輪指令 | 3715 / 8000（46.4%） |
| 計測輪の瞬間速度 | 1.457 m/s |
| 計測輪位置の約0.5秒間変位による速度 | 1.063 m/s |

各行の最大値は必ずしも同一時刻ではなく、最大値同士の比を応答倍率にしてはいけない。
衝突監視にはFootprintApproachの状態メッセージ16件、SlowZoneが14件ある。
これらは状態の記録件数であり、停止回数や減速継続時間ではない。
経路の加減速・姿勢制限と衝突監視の両方が速度を制約しており、設定上限だけの問題ではない。
検知点を実障害物か自己反射か区別できない問題は
[急停止の調査](ABRUPT_STOPS_20260915.md)を参照。

0.5秒変位は計測間隔150 ms超・時刻重複を含む窓を除外する。
瞬間値の外れ値を区別するための指標であり、計測輪から独立した実速度測定ではない。
2本目の1970年記録は最終指令が全てゼロで、応答倍率の同定対象にならない。

## 3 m/s要求と実速度は別々に検証する必要がある

現在の並進送信補正は0.38、換算は7202 UART単位／送信m/s。
純前後方向の3.0 m/s要求でも、`3 × 0.38 × 7202 = 8210.28`となり、
既存上限8000を超えて0.9744倍へ縮小される。
飽和しない要求速度は約2.923 m/sだが、これは実速度の上限を測定した値ではない。
補正を小さくして飽和を避けるだけでは、モーターへの出力も下がる。

2.0 m/s設定走行の時間を合わせた線形同定は、送信→計測輪で
前後2.6658倍・左右2.7298倍。これを8000まで外挿すると、前後2.961 m/s・左右3.032 m/s。
前後3 m/sに必要な指令の外挿は約8105、左右は約7915となる。
従来の完了走行からの外挿は前後3.007 m/s・左右2.979 m/sで、
方向や走行ごとの差だけでも3 m/s達成可否が入れ替わる。
実測は8000よりかなり低い範囲で、これらは保証値でも実測最高速度でもない。
車輪空転、負荷、電源降下、高速域の非線形応答を同定していない。

加速度0.85 m/s²、制動0.6375 m/s²、応答時間0.38秒という現行モデルでは、
3 m/sからの制動距離は8.199 m、静止からの加速を含めると13.493 m。
jerk、障害物、車体余白を含まないモデル計算で、実測停止距離ではない。
短い経路では速度上限を増やしても3 m/sに届かない。

## 修正と検証

`scripts/compare_field_response.py`は従来、UART車輪指令を8000以内に縮小しても、
機体モデルには縮小前の速度を入力していた。このまま高速化を試すと、
実際には送れない速度を達成したように評価する。
ミキサの縮小率を並進・旋回のモデル応答にも適用し、飽和の最小倍率とステップ数を追加した。
既存の非飽和領域の応答は保持する。

関連テスト53件成功。既存2 m/sの8 m経路12条件リプレイも合格した。
結果は`logs/three-mps/two-mps-regression.json`。これは3 m/sの試験ではない。
解析はROSを起動せず再現できる。

```bash
python3 scripts/audit_speed_target.py \
  ~/.ros/omni_autonomy_next/runs/19700101T000527.028726Z-6ae2b78a \
  ~/.ros/omni_autonomy_next/runs/19700101T002342.850864Z-0eb2b8a4 \
  ~/.ros/omni_autonomy_next/runs/20260914T093644.887096Z-0970b1be \
  --target 3 --output docs/three_mps_audit_20260915.json
```

実機3 m/sへ進むには、対象区間・使用可能な直線距離を決め、負荷を載せた状態で
高速域の指令対速度と停止距離を測定する必要がある。速度は校正した外部測距・距離と時間でも
照合し、瞬間的な計測輪ピークだけを到達の根拠にしない。
現在の記録だけを根拠にモーター上限・衝突監視・加減速度制限を緩める変更は採用しない。
